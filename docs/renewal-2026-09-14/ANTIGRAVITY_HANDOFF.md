## 2. 판단 근거와 범위

문제 재정의(PR)와 실행 가능성 평가(IS)를 함께 적용했습니다. 방문자의 첫 질문을 ‘어떤 기술인가’에서 ‘내 제품 자료를 어떻게 확인하는가’로 바꾸고, 현재 코드로 제공할 수 있는 행동부터 배치했습니다.

**확인한 사실:** 기존 랜딩에는 브라우저 내부에서 실행되는 텍스트 비교, 합성 시나리오 10개, 신청 API 호출 코드가 있습니다. 첫 화면은 원료 엑셀에서 신고 준비 초안을 생성한다고 설명했지만 같은 페이지의 개발 단계는 이를 예정 기능으로 설명했습니다. 주요 행동의 클래스와 적용 스타일에도 불일치가 있었습니다. 신청 처리 함수는 시작할 때 메시지에 `display:none`을 설정한 뒤 완료 시 해제하지 않았습니다. 기준과 라벨이 둘 다 비었을 때 일치로 반환하는 비교 분기도 있었습니다.

**추론:** 정보 입력과 확인 결과가 첫 화면에 명확하면 체험을 이해하기 쉬울 것으로 판단했습니다. 다만 실제 고객의 이해도나 신청 전환율이 개선되었다는 증거는 없습니다. 실사용자 테스트와 운영 분석은 별도로 필요합니다.

**디자인 가정:** 기존 포뮤 로고와 블루를 유지하면서, 디퓨저·향료·종이 자료의 촉감을 연결하면 대상 고객이 자신의 작업을 떠올리는 데 도움이 될 것으로 보았습니다. 이 이미지는 실제 고객, 실제 제품, 실제 실험 결과 또는 서류를 촬영한 것이 아닙니다.

**미확인:** 운영 사이트의 현재 배포 버전, 실제 신청 DB 영속 저장, 이메일 발송, 도메인 문의 주소의 수신 상태, 파일 비교 별도 페이지의 품질, 유료 기능 구현, 법규 데이터의 최신성과 적용 범위, 사용자 선호 모델 GPT2.5의 실제 사용 여부입니다. 새 결과를 해당 범위까지 검증했다고 표현하지 마세요.

고객 랜딩과 피치덱은 분리했습니다. 시장 규모·경쟁사 비용·출시 지연·라벨 폐기 손실 추정치는 현재 화면에서 제외했습니다. 새 규제 판단을 추가한 것이 아니며, 규제 적합성 검토를 수행한 것도 아닙니다. 유료 가격은 기존 제안가 99,000원/199,000원을 보존하되 출시 예정·검증 예정·현재 결제 불가 상태로 표시했습니다.

## 4. 구현 선택 12개와 검증 목적

1. 히어로 이미지와 카피를 별도 요소로 구현했습니다. 텍스트 수정·번역·접근성을 유지합니다.
2. 브랜드 마크는 새로 생성하지 않았습니다. 기존 로고와 색상 연속성을 유지합니다.
3. 사진은 핵심 3곳에만 배치했습니다. 결과표·가격·FAQ는 읽고 조작할 수 있는 HTML로 제공합니다.
4. 생성 이미지 원본은 문서 폴더에 보존하고, 웹에서는 WebP만 요청합니다. 원본 재편집과 전송량을 분리합니다.
5. 이미지마다 768/1536px 파일과 `srcset`을 제공합니다. 화면 폭에 맞는 자원을 선택합니다.
6. 히어로에는 `fetchpriority=high`, 하단에는 lazy loading을 사용합니다. 첫 화면에 우선순위를 줍니다.
7. 고객용 흐름에서 규제 시스템 탑재 숫자와 비용 추정 수치를 제거했습니다. 현재 코드로 확인하지 못한 기능 약속을 줄입니다.
8. 가격 카드마다 실제 목적지를 연결했습니다. 준비 중인 상품의 구매 성공 화면을 만들지 않습니다.
9. FAQ를 네이티브 접기 요소로 구현했습니다. 별도 JavaScript나 패키지 의존성을 늘리지 않습니다.
10. 포커스 표시와 reduced-motion 설정을 추가했습니다. 키보드 탐색 및 모션 감소 설정을 지원합니다.
11. 모바일 결과표는 영역 내부에서 가로 스크롤하고, 페이지 전체는 가로 넘침이 없도록 구성했습니다. 표의 항목 관계를 유지합니다.
12. 기존 신청 UI의 성공·오류 표시와 빈 기준값 처리 오류를 수정했습니다. 실제 결과에 맞는 피드백을 제공합니다.

현재 리뉴얼에는 React, Tailwind, GSAP, 새 런타임 패키지를 추가하지 않았습니다. 기존 Express 정적 페이지 구조를 유지하고 얇은 CSS 오버라이드 파일을 뒤에 로드합니다. 공간감은 사진·투명 오버레이·정적인 그림자로 표현했습니다. 연속 애니메이션과 스크롤 강제 이동은 없습니다. 기존 CSS를 재구성할 경우 오버라이드의 순서를 반드시 확인하세요.

## 5. 기능 수정 사항

- `compareVolumeField('', '', false)`와 텍스트의 기준·라벨 공란 조합은 `자료 부족`으로 반환합니다.
- 기존 10개 합성 시나리오의 기대 결과는 유지합니다. 이는 합성 입력의 기초 동작 검증이며 실자료 정확도나 규제 판단 정확도가 아닙니다.
- `handleSignup`의 `finally`에서 메시지 표시를 복구합니다. 성공·서버 오류·네트워크 실패가 사용자에게 보여야 합니다.
- 결과 요약과 신청 메시지에 `aria-live`를 추가했습니다.
- 이 작업은 신청 서버의 저장 로직을 바꾸지 않았습니다.

## 6. 검증과 한계

`verification.json`의 `assertions: PASS`를 확인하세요. 검증 스크립트는 일시적 정적 HTTP 서버를 127.0.0.1:4180에 열고 헤드리스 Chrome으로 실행한 뒤 종료합니다. 실제 신청 API는 호출하지 않고 응답을 가로챕니다.

검증 항목은 8개 섹션, 4개 FAQ, 이미지 로딩, 내부 앵커 존재, 10개 합성 시나리오, 빈 기준값, mL↔L, g↔mL 환산 보류, 음수 거부, 입력 수정 후 재비교, FAQ 열림, 신청 성공·네트워크 오류 메시지, reduced-motion, 320/390/768px 가로 넘침, 모바일 버튼 높이, JS 런타임 오류입니다. 데스크톱 1440px 전체 화면과 모바일 390px 상단·비교부·신청부를 눈으로 확인했습니다. 자동 검사에서 가로 넘침이 없더라도 좁은 버튼 안의 글자 줄바꿈 문제가 있었고, 시각 확인 후 수정했습니다.

보장하지 않는 범위: 실제 서버 DB 기록, 메일 발송, 운영 사이트 반영, 결제, 엑셀/PDF 별도 페이지 기능, 전체 WCAG 적합성, 실제 휴대전화 기기별 결과, 전환율 개선, Lighthouse 성능 점수입니다.

## 8. Antigravity에서 이어갈 작업

1. 실제 저장소에서 `git diff`와 이 문서, 최신 화면 캡처를 확인하세요. 기존 변경을 초기화하지 마세요.
2. 사용자가 원하는 이미지 모델 명칭을 반드시 유지해야 한다면 GPT2.5의 사용 가능 경로를 확인하세요. 현재 이미지를 그 모델로 생성했다고 기록하면 안 됩니다.
3. 데스크톱 1440px, 모바일 390px의 Hero·비교 버튼·FAQ·신청 화면을 먼저 열어 새 배치를 확인하세요.
4. 서버 검증은 별도 테스트 데이터 경로와 시험 환경에서 수행하세요. 실제 리드 DB에 테스트 신청을 넣지 마세요.
5. `server.js`에 기존 위험이 있습니다. `/api/report`는 인증 없이 최근 신청 정보와 CSV를 반환하는 코드이며, `saveDb`는 저장 실패를 잡고도 상위에서 성공 응답을 보낼 수 있습니다. 운영 배포 전 접근 제한과 저장 실패 전달을 점검해야 합니다. 이번 작업에서 운영 노출 여부를 조회하거나 실제 리드 데이터를 읽지 않았습니다.
6. 신청 정보의 실제 보유·삭제 정책, 개인정보 안내, 수신 동의 운영 방식을 확정하고 서비스 문서에 연결하세요. 존재하지 않는 정책이나 기간을 임의로 만들지 마세요.
7. 별도 `compare_v2.html`의 현행 기능을 확인한 뒤 랜딩의 ‘개발 예정’ 문구와 중복 여부를 정리하세요. 이번 작업에서는 링크를 보존했으며 별도 페이지를 수정·검증하지 않았습니다.
8. 사용자가 배포를 요청하면 확인된 대상 브랜치와 Render 연결을 확인한 후 진행하세요. 배포 성공 이후 공개 URL을 새로 열어 HTML·이미지·CTA를 재확인하고 로컬 완료와 공개 완료를 구분해 보고하세요.

## 9. 되돌리기

다른 수정이 없는지 diff를 확인한 후 `index.before.html`을 `public/index.html`로 복사하면 이전 랜딩이 복구됩니다. 리뉴얼 이미지와 CSS는 기존 파일과 이름이 겹치지 않습니다. 새 코드 위에 후속 수정이 있다면 전체 파일 복사 대신 해당 diff만 되돌리세요. 서버, 리드 DB, 피치덱 파일은 이 리뉴얼에서 수정하지 않았습니다.
